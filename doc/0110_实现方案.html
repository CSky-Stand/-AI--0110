3幻觉分类体系

判定总原则：system_reply 中的事实性断言与 knowledge_base 冲突；或 knowledge_base 为「无 / 未接入接口 / 需人工」时，回复仍给出具体事实、查询结果或完成承诺 → 判为幻觉。 判定单元是「断言」而非整句——这是 h04（半对半错）能被正确识别为「政策偏差」的关键。
#类型定义与触发要点样本严重度
1能力越界声称已执行系统未接入的查询/操作：物流、退款进度、改地址、升级工单、发券到账户h03 h10 h14 h18P0
2安全误导涉健康安全，与知识库注意事项相悖，可能造成健康风险h13P0
3优惠编造杜撰不存在的券/折扣/学生优惠，或承诺系统无权限的发放动作h05 h19P0
4政策编造整条政策与知识库无对应或完全相反（退货政策、发票、发货时效等）h01P0
5政策偏差政策部分正确、部分错误（如电子发票对、纸质发票错）h04 h08P1
6参数编造产品规格与知识库不符：版本号、接口、材质、保修期、功能h02 h06 h09 h17P1
7信息编造杜撰实体信息：退货地址/收件人、线下门店、品牌关联h07 h11 h15P1
8信息遗漏关键信息未告知导致建议不准（如「30% 用户反馈偏大」被说成「不偏」）h20P2
与 ground_truth 对齐：本方案的 8 类名称与 task4_ground_truth.json 的 hallucination_type 完全同名， 因此「类型判对率」可直接字符串比对，无需映射表。严重度口径：P0=涉及资金/健康/合规或用户会据此行动；P1=误导购买决策、引发售后纠纷；P2=建议质量下降。

5规则引擎设计

规则引擎是默认主干，零依赖、可复现、每条命中都附证据片段。7 大检查器：

检查器规则要点证据片段示例覆盖
能力越界回复含动作完成词（查了/已查到/已帮您修改/已升级/已在处理中/发到您账户/已为）→ 触发；知识库含「无 / 未接入 / 需人工 / 不具备」→ 判真reply「我帮您查了一下」 vs KB「客服系统未接入物流查询接口」h03 h10 h14 h18
参数编造抽取产品参数对（蓝牙版本/接口/材质/保修期/功能 NFC/延迟/连接数）与知识库比对，值不同 → 判真reply「蓝牙 5.3」 vs KB「蓝牙 5.0」h02 h06 h09 h17
政策编造/偏差抽取政策条款（天数、运费承担、发货时效、快递名、发票类型）与知识库比对；全部冲突=政策编造，部分冲突=政策偏差reply「纸质发票」 vs KB「暂不支持纸质发票」；reply「电子发票」命中 KBh01（编造）h04 h08（偏差）
优惠编造回复含「满 X 减 Y / 券 / 折扣 / 学生优惠 / 认证」而知识库无对应活动 → 判真reply「满 300 减 50」 vs KB「满 200 减 20、满 500 减 60」h05 h19
信息编造回复出现地址/收件人/城市门店/品牌关联等实体，知识库无对应或明确「不得口头告知」→ 判真reply「杭州文三路 478 号 张经理」 vs KB「地址需系统匹配后短信发送」h07 h11 h15
安全误导知识库含「注意事项/孕妇/咨询医生/风险」等提示，回复却给「放心使用/安全」肯定结论 → 判真reply「孕妇可以放心使用」 vs KB「含视黄醇衍生物，孕妇建议咨询医生」h13
信息遗漏知识库含「约 X% 反馈 / 注意事项」等影响建议的关键信息，回复给出相反结论或省略 → 判真（标 P2，置信度低）reply「尺码标准不偏」 vs KB「约 30% 用户反馈偏大半码」h20

负样本白名单（防止 h12 / h16 误报）

  • 否定句识别：回复「不支持货到付款」为否定断言，与 KB「不支持货到付款」一致，不触发政策类规则（h12）。
  • 一致表述识别：回复与 KB 同义（色差说明），归一化后相等则判正常（h16）。
  • 动作未完成识别：「建议您 / 您可以 / 需要转人工」等引导语不算能力越界。

6LLM 复核设计

接口契约（OpenAI 兼容）：POST {base_url}/chat/completions，Bearer 认证，temperature=0，强制 JSON 输出。

输入：knowledge_base + system_reply（单条）；输出 Schema：

{
  "is_hallucination": true,
  "type": "参数编造",            // 必须取自 8 类枚举；否则按解析失败处理
  "severity": "P1",
  "evidence_span": "蓝牙 5.3",   // 回复中的原文证据
  "reason": "知识库为蓝牙 5.0，回复给出 5.3"
}

复核触发策略（控制成本与波动）

  • 规则高置信命中（如数值精确冲突）→ 不调 LLM，直接采信规则结果。
  • 规则低置信命中（h20 遗漏类）或未命中但回复含数字/政策词 → 交 LLM 复核。
  • 未配置 key / 网络错误 / 超时（5s）/ JSON 解析失败 → 自动降级为规则结果，并在 verdict 中标注 method=rule|llm|fallback（fallback 即任务允许的 mock 模式）。

7判定合并与证据输出

每条 verdict 输出以下字段，保证可复核、可解释：

字段说明
idh01–h20
is_hallucinationbool，最终判定（正类=幻觉）
type8 类之一；正常回复为 null
severityP0/P1/P2；正常为 null
evidence回复原文片段 + 知识库对应片段（两者对照）
confidencehigh / medium / low（低置信进「争议 case」）
methodrule / llm / fallback
disputedbool：h04、h20 标 true，单列争议

8评估口径与指标

正类 = is_hallucination=true（18 正 / 2 负）。给出两套口径：

口径规则差异
严格口径18 条正样本全部必须检出（含 h04、h20）对「遗漏」最苛刻，漏检 h20 即扣 Recall
宽松口径h20（信息遗漏）不计入必须检出项17 正 / 2 负，反映「编造型幻觉」的检出能力

指标与清单

  • 核心指标：Accuracy、Precision、Recall、F1（两套口径各一份）。
  • 混淆矩阵：TP / FP / FN / TN，负样本 h12、h16 必须落 TN。
  • 类型判对率：检出且 type 与 ground_truth 同名一致的比例（8 类同名，直接比对）。
  • 漏检清单：ground_truth=true 但判 false 的条目 + 原因。
  • 误报清单：ground_truth=false 但判 true 的条目 + 原因。
  • 争议 case 专项：h04、h20 单列，展示规则与 LLM 的判定差异。

9预期误判分析与对策

case易误判原因对策
h04半对半错：电子发票正确、纸质发票错误，整句判定会漏断言级拆分：逐断言比对，命中+冲突并存 → 政策偏差

h07地址是「具体但无从验证」的实体，规则靠词表可检出，LLM 也能判，但需注意 KB 是「不得口头告知」而非「地址不存在」规则命中文案「短信方式发送/不可口头告知」而非仅看地址真假

12测试策略

  • 单元测试：extract（断言/数字/否定句）、rules（7 检查器逐一用 h01–h20 中的代表样本做正/负断言）、evaluate（指标计算，含两套口径）。
  • 冒烟测试：读取 doc/ 真实附件，跑完整管线，对 20 条结果做 golden 断言——目标 strict 口径 Recall=100%（18/18），Precision 无负样本误报；两套口径数值与 report 输出一致。
  • 连通性测试（不自动跑）：go run ./cmd/detect llmcheck 单发一次请求验证 base_url/model/key，输出可用模型列表。
